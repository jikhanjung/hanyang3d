# 119 — 운영 콘텐츠 DB 전환과 백업 연결

## 범위

기록 118의 프레임워크를 운영으로 전환한다. 관리자 ID는 사용자 요청대로 `admin`이다. 웹은 v0.3.0, 멀티플레이는 v0.2.4를 유지한다.

## 구현

- `MULTIPLAYER_IMAGE_TAG`를 웹 `IMAGE_TAG`에서 분리하고, `--web-only` 빌드는 웹과 데이터 묶음만 만든다. 현재 공간 호환 키 `v0.2.4`를 웹 버전과 분리해 기존 브라우저와 같은 공간을 사용한다.
- DB 모드 배포는 웹 중지 → 기존 DB의 검증 백업 → 일회용 컨테이너 migration/최초 가져오기 → 서비스 확인 순서다. 재가져오기는 기존 편집 데이터를 바꾸지 않는다.
- 별도 콘텐츠 볼륨과 HTTPS 관리자 쿠키를 사용한다. 비밀키·기존 환경 설정은 보존한다.
- 시간별 스냅샷과 서비스 설정을 읽기 전용 SSH export 도구로 내보낸다. 최신성·무결성·외래 키·세션 제거 여부를 확인한 사본만 전송한다.
- 개발 호스트의 실행본은 `system-operation/m710q/backup-hanyang3d.py`에 둔다. 로컬 일간 30일·NAS 90일 이후 월초 보존, 잘못된 사본 미채택, 임시 파일 뒤 원자적 교체를 사용한다. 메시지 전송 기능은 추가하지 않는다.

## 검증 및 운영 기록

- 소스 `3c12cc8`을 커밋·푸시하고 웹 v0.3.0 이미지만 빌드·배포했다. 웹 digest: `sha256:7e82ad170653af4459dd92a1900c735bb8b6174578b78472cbe889fbfc2d5114`.
- 멀티플레이 v0.2.4 digest `sha256:9b9db8007fa3f9f7bb873bbd3621aa54e1075c1bf146ecfc13c70ac6b0c6f29f`, 기존 컨테이너 ID가 배포 전후 동일했다. 새 멀티플레이 이미지는 만들지 않았다.
- Django 27개·릴리스 환경 보존 3개 검사, 이미지 파일 모드/DB 모드 검사, 재시작 후 편집 보존·재가져오기 무변경·백업 검사를 통과했다.
- 운영 `/healthz`: v0.3.0, database, 건물 103·공개 이야기 33, 리소스 파일 93, status ok. DB의 상세 설명 102·전체 리소스 108도 확인했다.
- HTTPS `admin` 로그인과 네 가지 목록, 비공개 이야기 생성/조회/삭제, secure 쿠키 검사 통과. 임시 비밀번호는 로컬 Git 제외 `.env.admin`(600)에 저장했으며 로그·문서에 출력하지 않았다.
- 운영 3D 브라우저 검사에서 이야기 33편 연결과 홍화문 이야기·출처 표시를 확인했다.
- 기존 운영 설정을 `/srv/hanyang3d/backups/pre-v0.3.0-20260915-103728`에 보존하고 `.env.django` 동일성을 확인했다.
- `/etc/cron.d/hanyang3d-content`에 매시 백업을 설치했고 첫 스냅샷과 다음 정각의 자동 실행을 확인했다.
- 2026-09-15 19:59(KST) 첫 일간 pull에서 개발 호스트·NAS 채택 모두 성공했다. 기존 크론을 보존하고 매일 05:15(KST) 실행을 등록했다. 로컬 30일·NAS 90일 이후 월초 보존 정책이다.
- 운영 스냅샷 `content_20260915_110001_434765.sqlite3`의 사본을 네트워크 없는 일회용 컨테이너에 복원해 건수·관리자·세션 0행·수정 후 재조회 검사를 통과했다. 운영 DB는 복원 대상으로 쓰지 않았다.

## 사용과 한계

이야기·건물 설명·기존 리소스 연결은 백오피스에서 편집하며 다음 페이지 요청부터 반영된다. 이미 열린 지도는 새로고침이 필요하다. 새 모형 코드·지형 리소스·서버 로직 변경은 해당 이미지 배포가 필요하다. DB 스키마를 되돌리는 복원은 별도 작업이며 이미지 롤백만으로 DB까지 되돌리지 않는다. 외부 메시지 알림은 연결하지 않았다.
