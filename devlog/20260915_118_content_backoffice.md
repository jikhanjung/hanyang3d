# 118 — 콘텐츠 DB·리소스 목록·백오피스 기반

## 요청

이야기·건물 목록·건물 설명을 DB에서 관리하고, 건물 모형은 리소스로 보관하면서 그 목록과 연결을 백오피스에서 편집할 수 있게 한다. 백업은 형제 프로젝트 `../fsis2026`을 참고한다.

## 구현

- SQLite 콘텐츠 DB와 Django 관리자(`/backoffice/`). 모델별 권한, 검색·필터, 수정 시각, 관리자 변경 이력, 기본 인증·CSRF를 사용한다.
- Building: 고정 ID·이름·분류·짧은 소개·존재 시기·1750년 설명·상세 설명 연결·모형 리소스·배치 설정·공개 여부.
- GuideSection: 기존 안내 Markdown을 제목/분류/건물 설명 절로 보존. 표나 여러 건물의 공동 설명도 누락하지 않고 공유 연결한다.
- Story·Citation: 건물 외래 키 또는 실제 다리·동네 선택, 출처 인라인 편집. 백오피스에서 출처 없는 이야기 공개를 막는다.
- Resource: 모형 생성기 15개와 공개 파일 93개의 목록. 실행 코드와 파일 본문은 DB가 아니라 버전 리소스로 유지한다. 공개 allowlist와 생성기/경로 대응을 검증하며 임의 서버 파일을 공개하지 않는다.
- 지도와 건물 안내는 DB의 공개 콘텐츠를 읽는다. 다음 페이지 요청부터 편집이 반영되며 새 이미지 배포가 필요 없다. 이미 열린 지도는 새로고침해야 한다.
- 원도 좌표·모형 매개변수는 기존 JSON을 보존하되 별도 이름·분류·모형 필드와 충돌하는 값, 잘못된 좌표·치수·원도 해시를 검증한다. 성문·종묘 생성도 DB의 선택된 모형을 따른다.
- 상세 설명 Markdown의 HTML은 escape하며 위험하거나 잘못된 링크 스킴은 링크로 만들지 않는다.

## 초기 자료와 운영 편집 보존

`migrate` 뒤 `import_content`로 건물 103곳·이야기 33편·상세 설명 102개·리소스 108개를 가져온다. 건물의 모든 기존 정보·공간 필드, 이야기 JSON 전체, 안내 HTML을 원본과 비교했다.

가져오기는 원자적 트랜잭션이며 `--dry-run`을 제공한다. 빈 콘텐츠 DB에서만 최초 실행되고, 완료 뒤에는 명령을 다시 실행해도 운영 수정·삭제를 덮어쓰거나 복구하지 않는다. 콘텐츠 JSON 내보내기는 계정·세션을 제외한다.

로컬 DB는 `data/content.sqlite3`이며 Git·Docker에서 제외한다. 고정 관리자 비밀번호는 만들지 않는다. 테스트 계정은 일회용 테스트 DB 안에만 생성한다.

## fsis2026 백업 참고

읽은 구현·문서: `scripts/backup_db.py`, `scripts/test_backup_db.py`, `docs/operation_manual/backup.md`, 개발 기록 220·222. 특히 Python SQLite 연결 context manager가 연결 자체를 닫지 않는 점과 WAL 모드가 사본에도 복사되는 점을 반영해, 명시적 close와 DELETE journal mode로 독립 스냅샷을 만든다.

`deploy/host/backup_content.py`는 표준 라이브러리만 사용하는 정본이며 Django 관리 명령도 같은 구현을 호출한다.

- online backup API, 무결성·외래 키 검사 후 원자적 채택.
- 사본의 세션 제거 후 VACUUM. 운영 DB·로그인 세션은 변경하지 않음.
- 원본 부재·손상·디스크 부족·검증 실패 시 이전 백업을 prune하지 않음.
- 같은 시간 재실행은 최신 검증본만 남겨 서로 다른 24시간의 복원 지점을 유지. 최소 여유 공간 5 GiB.
- 실패 플래그를 healthz의 degraded(200)로 표시. readiness의 DB 연결 실패·미초기화는 unhealthy(503). smoke는 ok만 통과.
- 백업 파일 600·디렉터리 700, 파일 잠금, 별도 손상 증거 1개. 웹에 백업 디렉터리를 마운트하지 않음.

배포 전·시간별·일간 pull/NAS 레인과 복원 절차를 [백업 안내](../docs/content_backup.md)에 정리했다. fsis의 일간 실행본은 `system-operation`이 정본이므로 여기에는 작동하지 않는 복사본을 만들지 않았다.

## 검증 결과

- Django 26개 테스트 통과(기존 15 + 콘텐츠·권한·초기 이전·백업 11).
- `manage.py check`, migration 변경 누락 검사, Python 컴파일, 셸 문법, `git diff --check` 통과.
- 격리된 DB의 Playwright: 관리자 로그인 → 건물 소개·이야기 제목·상세 설명 저장 → 안내와 실제 3D 지도 반영, 건물 103개 표시, 브라우저 오류 없음.
- 별도 로컬 이미지 `hanyang3d-content-check:v0.2.4`: 파일 모드의 기존 컨테이너 검사, 26개 테스트, 자원 93개, UID 10001 통과.
- 일회용 Docker 볼륨의 DB 모드: migration·가져오기, 관리자 로그인 페이지·CSS·안내, 건물 103·이야기 33 확인. 웹 컨테이너 재시작 뒤 편집 보존, 재가져오기 뒤 편집 보존, 검증 백업까지 통과.
- WAL 사본 복원 후 읽기·쓰기, 과거 삭제된 세션 바이트 제거, 원본 부재/손상 시 25개 이전 백업 보존, 정상 회복 후 실패 플래그 해제·24개 보존 검증.

## 배포 상태와 후속

운영 v0.2.4 배포와 커밋/푸시는 앞선 기록 117에서 완료했다. 이번 변경은 DB 관리 **프레임워크와 로컬 검증**이며 운영 DB 전환은 하지 않았다. Docker는 기존 운영 호환용 파일 모드를 기본값으로 유지한다. DB용 Compose override와 전환 절차는 [백오피스 안내](../docs/backoffice.md)에 있다.

DB 모드는 별도 쓰기 볼륨과 안정된 운영 비밀키, 관리자 계정, 실제 배포 전·정기·오프사이트 백업 설치가 필요하다. 시작 시 migration 누락을 검사하며 자동으로 migration하거나 초기 자료를 다시 쓰지 않는다. 기존 deploy.sh만으로 DB migration·백업을 자동화했다고 간주하지 않는다.

외부 모형 업로드/GLB 뷰어, 멀티플레이 독립 이미지 버전, 운영 크론·NAS 연결은 이번 범위에 포함하지 않았다. 모형 코드·지형은 계속 이미지/지도 파일 레인에서 관리한다.
