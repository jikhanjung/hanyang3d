# 087 — 첫 로딩 시간 줄이기

사용자가 첫 로딩이 오래 걸린다고 했다.

## 측정

- 내려받는 자료는 38개 요청, 약 5.5 MB로 네트워크는 1초 안팎이었다. 오래 걸린 것은 브라우저 안의 계산이다.
- 개발 호스트의 헤드리스 Chromium은 기본이 SwiftShader라 렌더링 시간이 부풀려진다. `--use-angle=vulkan`(llvmpipe)으로 띄워 비교 기준으로 삼았다. 벤치 스크립트는 로딩 단계별 시간(`terrainLoading.history`)을 읽는다.
- CPU 프로파일에서 자바스크립트 병목은 두 곳이었다.
  1. `TerrainSupport.footprintRange`: 건물 88곳의 바닥 높이를 구할 때마다 지형·지도 표면 삼각형 **전체**(수십만 개)를 돌았고, 삼각형마다 배열을 여러 개 만든 뒤에야 먼 삼각형을 걸렀다. 처음 배치와 하천 보정(`applyChannel`) 때 두 번 되풀이됐다.
  2. 하천 지형 워커: 지형을 16만 → 121만 꼭짓점으로 잘게 나누면서, 삼각형과 꼭짓점마다 하천 경로 74개 구간을 모두 비교했다(`ChannelTerrain.nearest`).

## 고친 것

결과가 한 치도 달라지지 않는 방법만 썼다.

- `ground_support.js`: 삼각형 좌표 원본으로 먼저 범위를 비교해, 먼 삼각형은 배열을 만들지 않고 건너뛴다.
- `city_wall.js`의 X/Z 격자 색인 `surfaceIndex`를 내보내, 건물 바닥 계산(처음 배치와 `applyChannel`)이 건물 주변 칸의 삼각형만 보게 했다. 성벽·시전·주택·수목은 이미 이 색인을 쓰고 있었다.
- `channel_terrain.js`에 `segmentGrid`·`nearestWithin`을 더했다. 하천 구간을 격자에 넣고 주변 칸 구간만 비교한다. 참 최단거리가 기준 거리보다 가까우면 기존 `nearest`와 같은 식·같은 순서로 같은 값을 돌려주고, 멀면 무한대를 돌려준다.
  - 세분화 판정(`중심 거리 < 반경 + 변 길이`)은 기준 거리를 그 값으로 주어 판정이 같다.
  - 워커의 꼭짓점별 거리는 가장 넓은 폭+20 m를 기준으로 한다. 파기는 폭+20 m 안에서만 일어나므로 멀리 있는 꼭짓점은 무한대 거리여도 원래 높이 그대로다.
- 워커 출력에서 `slice`·펼침 연산을 없앴다.
- 워커 시간과 꼭짓점 수를 `terrainLoading.refine`에 남기는 읽기 전용 진단을 넣었다.

## 결과 (llvmpipe 기준, 같은 기기)

| 단계 | 이전(운영 v0.1.16) | 이후 |
| --- | --- | --- |
| 주요 건물·문 | 9.1 s | 1.0 s |
| 하천 주변 지형·성벽·길 | 23.7 s | 6.0 s (워커 2.9 s) |
| 주택·상가 | 2.6 s | 1.4 s |
| 전체 | 38.1 s | 12.5 s |

- 새 코드와 운영 v0.1.16을 같은 브라우저에서 띄워, 지형 꼭짓점 표본, 건물 88곳의 바닥 높이, 성벽 구간, 표시된 주택 바닥, 수목 수가 모두 같음을 확인했다.
- Node로 기존 `channel_terrain.js`와 새 파일을 나란히 불러, 무작위 점 20만 개의 최단거리 판정과 약 100만 꼭짓점 세분화 출력이 같음을 확인했다.
- 실제 GPU가 있는 사용자 기기에서는 렌더링 몫이 더 작아 비율은 달라질 수 있다.

## 더 줄일 수 있는 것 (이번에는 안 함)

- 하천 지형은 세분화 출력이 삼각형마다 꼭짓점을 따로 가져 121만 개가 된다. 꼭짓점을 공유하게 하면 메모리·업로드·보정 계산이 크게 줄지만 법선이 매끈해져 모양이 조금 달라진다.
- 세분화 결과를 미리 계산해 파일로 두면 워커 2.9 s가 사라진다.
- 정적 파일이 `no-cache`라 재방문 때마다 재검증 요청이 나간다. 버전 경로와 긴 캐시로 바꿀 수 있다.
